= ADR 0006: stable tagへの直接公開
:status: accepted

== 文脈

このrepositoryは個人開発であり、stable公開前の候補成果物に対して導入、完全性および由来を
自動検証します。RCとstableを別tagで公開すると、同等の検証とバージョン同期を二度運用する一方、
追加の独立した受け入れ情報は得られません。

== 決定

release candidate tagを受理しません。通常のversion更新では機械可読なrelease intentを``preparing``にし、
すべての変更を統合した後のfinalization Pull Requestだけが``ready``へ変更します。手動workflowには、
このPull Requestのsquash commitを候補SHAとして渡します。workflowはreview済みのintent、未統合Pull Requestが
ないことおよび同じSHAのmain candidateを検証し、そのSHAを公開対象として固定します。

検証後は公開jobが``vX.Y.Z`` tagを一度だけ作成し、同じworkflow runでstable GitHub Releaseを公開します。
公開後の修正はtagを付け替えず、新しいstableなバージョンとして公開します。

書き込み権限はworkflow tokenが持ちます。``github-release`` Environmentが、その権限を使える範囲を限定する
権限・監査境界です。release用workflowで``contents: write``を持つjobはこの公開jobだけであり、Environmentの
deployment branch制限によって、許可したbranchから開始したrunだけがこのjobへ到達します。

tagを作成できる主体を公開jobだけに限る仕組みは、まだありません。専用のGitHub Appを唯一のbypass対象とする
repository rulesetでそれを実現できますが、Appの作成、インストールおよび鍵の管理という運用費用が伴います。
現時点ではその費用に見合わないと判断し、Environmentによる限定にとどめています。tagの作成経路を機械的に
強制する必要が生じた時点で再評価します。

== 帰結

公開経路はstable SemVerだけを扱います。finalization Pull Requestとtag作成前の自動検査を公開条件とし、
公開後の修正は新しいバージョンで行うため、tag後の検査結果でtagを変更しません。
公開開始後に人が承認を挟む停止点はありません。review済みのfinalization Pull Requestを指定した
``workflow_dispatch``を公開判断とし、その開始時点でmain先端だった候補SHAを以後の公開identityとして扱います。
開始後にmainが進んでも候補SHAと成果物は差し替えません。
未知の環境での長期試験が必要になった場合だけ、通常release trainとは別の検証用branchまたは
事前配布を明示的に設計します。
