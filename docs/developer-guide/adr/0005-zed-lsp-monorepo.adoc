= ADR 0005: Zed LSPのmonorepo管理
:status: accepted

== 文脈

Zed extensionは、同じReleaseのmanifest、checksumおよびattestationを検証してLanguage Server binaryを取得します。
Core、LSP、Zed extension、browser artifactおよびNix packageは一つのrelease manifestとconformance fixtureを共有し、
同一release trainで整合性を確保する必要があります。

Zed extensionとLanguage Serverを別repositoryへ分離すると、Zed固有のreviewと公開を独立できる可能性があります。一方で、
releaseのバージョン、binary provenance、LSP protocol、Tree-sitter queryおよびrollbackの整合性をrepository間で新たに
保証しなければなりません。

== 決定

Zed extensionとLanguage ServerはAdocWeave monorepoに維持し、独立repositoryおよび独立release trainは導入しません。
Zed固有の責務はmonorepo内に局所化します。Core、LSPおよびZedにまたがる変更では、
同一release trainで成果物と利用者向け仕様の整合性を維持します。

== 非採用案

Zed extensionだけを別repositoryで公開し、LSP binaryを本体Releaseから取得する案は採用しません。この案ではextensionと
binaryのバージョン不一致、artifact provenance、offline cacheおよびrollbackの障害を二つのrelease履歴にまたがって
調査する必要があり、現在の開発規模に対して運用コストが大きいです。

== 再評価条件

次のいずれかを満たしたときだけ、この決定を再評価します。

* 連続する3回のrelease trainにおける、CoreまたはLSP binaryを変更しないZed extension単独公開の
  各回1件以上の必要性
* 連続する10回のmain runにおける、Zed固有jobによるCI critical path中央値の50%超の占有と、
  monorepo内のjob分離による解消不能
* Zed extensionを本体と異なる所有者、権限境界またはsecurity response期限で運用する
  明確な要件の発生

再評価では、repository分離前にCore/LSP/Zedの互換性範囲、artifact digest、ソースのrevisionおよびrollback対象を
自動検証する仕組みを設計します。

== 帰結

一つのcommit、release manifestおよびGitHub Releaseで利用者が必要とする成果物を追跡できます。
横断変更のCIは必要ですが、Zed固有の変更はmonorepo内の独立したtestとartifact jobへ局所化できます。
