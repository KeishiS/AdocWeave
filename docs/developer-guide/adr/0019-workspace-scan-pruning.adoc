= ADR 0019: 初期ワークスペース走査とリソース読込の分離

== 状態

採用

== 背景

Language Serverは、ワークスペース内の``.adoc``ファイルを解析の起点として登録するため、起動時に
ディレクトリを再帰的に走査します。仮想環境、依存パッケージおよびビルド結果を含むワークスペースでは、
解析対象ではないファイルによって10万件の走査上限へ達することがあります。

走査からディレクトリを除外するだけでは、除外したディレクトリ内の文書をincludeできなくなります。
一方、除外規則をファイルシステムのアクセス権限として扱うと、明示的に開いた文書やCLI入力にも影響し、
初期走査の負荷を抑えるという目的を超えて既存の動作を変えてしまいます。

== 決定

``workspace.scan.exclude``は、Language Serverの初期ディレクトリ走査で解析の起点を見つける処理だけに
適用します。各workspace folder直下の設定を走査前に読み、一致した実ディレクトリを内容の列挙前に
枝刈りします。除外したディレクトリ自体は既存の走査件数へ数え、その中身は数えません。

patternはOSに依存しない規則で検証し、ワークスペースのルートからの相対位置へ照合します。区切りは``/``、
照合は大文字と小文字を区別し、``*``と``?``は一つの区間、単独の``**``は複数の区間に一致します。
絶対パス、親ディレクトリへの移動およびOS固有の区切りは拒否します。
設定時にpatternを照合用tokenへ変換し、1件あたり1024文字、全体で4096文字に制限します。Unix上の
非UTF-8区間は通常の文字patternに一致させず、``**``だけがその階層を通過できます。

除外規則はファイルシステムのアクセス権限ではありません。明示的に開いた文書、CLIへ直接渡した入力および
include先は読み込めます。file watcherは既知の文書とinclude先を更新しますが、通知だけを理由に除外範囲の
新しい文書を解析の起点へ登録しません。開いた解析の起点を前処理した結果、includeに必要な文書がsnapshotに
ない場合だけ、従来のworkspace root、``resources.roots``、symlink検査およびresource上限を使って読み込みます。
初期走査では未open文書を前処理せず、必要性は開いた文書の解析workerで判定します。読み込んだinclude先は
解析の起点として登録しません。

初期走査の後に編集で新しいincludeが追加された場合は、解析workerが返す不足resourceの論理IDを使います。
main loopは解析対象の文書revisionとworkspace世代が現在も有効であることを確認し、不足resourceを同じ権限と
上限で読み込んでから、通常の編集用待機時間を挟まず新しい解析jobを実行します。文書revisionが古い場合と
許可範囲外の要求では読み込みません。別文書のresource追加でworkspace世代だけが古くなった場合は、現在の
snapshotでjobを作り直し、複数のopen文書を同じ世代へ収束させます。同じ文書revisionでは取得を試みた論理IDを
記録し、同じ対象を繰り返し読みません。

workspace folderが入れ子の場合、外側のfolderの走査では内側のfolderを枝刈りし、内側のfolder自身の走査へ
委ねます。各folderの走査方針を一つのroot相対名前空間へ限定し、重複走査による除外規則の迂回を防ぎます。

directoryの列挙と走査件数の管理は引き続き``adocweave-host``が所有します。設定の照合結果は、
ディレクトリを列挙する前に呼ぶ判定関数としてhostへ渡します。parser、HTML compilerおよびCLIは
この判定関数を渡さないため、入力の選択方法は変わりません。

== 結果

利用者は大きな生成物のディレクトリを初期走査から除外しながら、必要な文書を明示的に開くかincludeできます。
10万件という安全上限と、ファイルシステムへのアクセスを制限する既存の境界は維持されます。

走査前にworkspace folder直下の設定を読む経路と、include先を必要に応じて追加する経路が増えます。
初期化、設定変更およびworkspace folder変更は、同じ世代管理されたworker経路で走査します。走査workerは
同時に1件だけ実行し、設定またはworkspace folderが続けて変わった場合も、保留する再走査を1件にまとめます。
古い設定による走査は協調的に取り消しますが、そのworkerの終了を確認する前に次のworkerを開始しません。

走査中にfile watcherから通常文書の通知を受けた場合は、進行中の走査を完了させます。通知されたURIは
重複をまとめた上限付きの記録へ保持し、走査結果を組み込んだ直後に再適用します。一つの通知batchも記録と同じ
1万URI、URI文字列の合計1 MiBを上限とします。記録または通知batchの上限を超えた場合だけ
進行中の走査結果を破棄し、現在のincremental workspace状態を保って上限超過を診断します。同じ通知量による
再走査を繰り返さず、最後の通知から100ミリ秒が経過した後に世代付きの再走査を1件だけ保留します。これにより、
待機処理も一つだけとし、後続通知では取り消して置き換えます。通知が続いても個々の走査が終了し、走査worker、
待機処理および保留処理の数が増え続けません。走査後の変更再適用が完全走査を必要とする場合は同じ回復経路へ戻し、
回復予約には必要な最小の走査世代を保持します。その世代より古い走査では予約を解除せず、通知を完全には再適用
できない場合は進行中の古い走査結果も組み込みません。shutdownとserver状態の破棄では待機処理を取り消します。
待機時間が走査中に満了した場合も、必要な世代を満たす走査の変更記録は完了まで保持します。変更記録を破棄して
後続走査へ移る場合は、進行中の結果も不採用にします。取消済みまたは古い世代の結果、
記録の上限を超えた世代の結果および途中まで読んだ結果はworkspace snapshotとして扱いません。

watch読込errorは128 URIか、URIとerror文字列の合計64 KiBまで保持します。上限超過時は同じ待機処理で
再走査し、成功した完全なsnapshotだけが上限超過診断を解除します。回復用の走査が失敗した場合は、次の
watch通知を受けてから再び待機するため、修復前の連続再試行と修復後の回復不能をどちらも避けます。
