= Zed開発環境

この文書では、リポジトリの作業treeからZed拡張とLanguage Serverを検証するための環境、
操作手順および確認項目を定義します。公開Extension Galleryからの導入手順ではありません。

Zedの開発拡張は次のfileを入口とします。
link:../../editors/zed/extension.toml[`editors/zed/extension.toml`]
拡張はAsciiDoc用Tree-sitter grammar、inline grammarおよびhighlight／injection queryを提供します。
開発手順ではworktreeの``PATH``から``adocweave-lsp``を探して起動するため、
公開Releaseからmanaged binaryをdownloadしません。公開版におけるbinaryの選択と取得は
xref:../user-guide/release-installation.adoc#zed-installation[Zedへの導入]を参照します。

== 前提条件

次を利用できることを確認します。

* Zedと``zed``または``zeditor`` CLI（Linuxではdistributionにより異なるbinary名）
* `cargo`、`rustc`、``rustfmt``およびClippy
* ``rustup``で管理されたRust toolchainと、Zedが要求するWASM target
* C compiler（Nix開発環境では``stdenv.cc``に含まれるもの）
* 初回のgrammar、WASI SDKおよびRust依存関係を取得するためのnetwork接続

Zed公式文書は、Rustを含む開発拡張のbuildに``rustup``で導入したRustを要求しています。Zedが
`wasm32-wasip2` targetの導入に失敗する場合は、Zedが参照するtoolchainで次を実行します。

[source,console]
----
rustup target add wasm32-wasip2
----

リポジトリのNix環境を使う場合は、先に次を実行します。

[source,console]
----
nix develop
----

Nix shellのRust toolchainでリポジトリ本体をbuildできても、Zedの開発拡張builderは別processとして
``rustup``とWASM targetを探します。``nix develop``だけで``wasm32-wasip2``導入エラーが解消するとは限りません。

== 隔離したZed利用者データによる推奨手順

通常利用しているZedの拡張、設定、DBおよびcacheへ影響させないため、workspace外の一時directoryを
user data directoryとして使います。workspace内へ置くと、Zedのworktree監視が拡張builder自身のWASI SDK、
grammarおよびcacheの更新を走査し、一時的なsymlinkやinotify watchについて無関係なerror／warningを記録します。

. リポジトリrootでLanguage ServerとZed拡張を検査します。

[source,console]
----
cargo build -p adocweave-lsp
cargo make check-zed
cargo make test-zed
cargo make check-zed-wasm
----

``test-zed``はmanaged binaryのmanifest検査、hash不一致、archive抽出、cache改変および更新失敗時の
rollbackも確認します。

. 同じshellでLanguage Serverを``PATH``へ追加し、隔離したZedをforegroundで起動します。

[source,console]
----
export PATH="$PWD/target/debug:$PATH"
ZED_DEV_DATA="$(mktemp -d /tmp/adocweave-zed-dev.XXXXXX)"
printf '%s\n' "$ZED_DEV_DATA"
if command -v zed >/dev/null; then
  ZED_CLI=zed
elif command -v zeditor >/dev/null; then
  ZED_CLI=zeditor
else
  printf '%s\n' 'Zed CLIが見つかりません' >&2
  exit 1
fi
"$ZED_CLI" --foreground --user-data-dir "$ZED_DEV_DATA" .
----

``--foreground``は必須ではありませんが、拡張buildとLanguage Server起動のlogをterminalで確認できます。
Zedを別のlauncherや既存processから開くと、上記shellの``PATH``を継承しないことがあります。

. ZedでExtension Galleryを開き、``Install Dev Extension``を選びます。コマンドパレットから
  ``zed: install dev extension``を実行しても構いません。
. directory選択画面で、リポジトリrootではなく``editors/zed``を選びます。このdirectoryには
  ``extension.toml``があります。
. ``fixtures/zed/manual.adoc``を開きます。

初回導入時、ZedはRust拡張をWebAssembly componentへbuildし、``extension.toml``に固定した
``tree-sitter-asciidoc``を取得してgrammarをbuildします。Tree-sitterのparserはgrammar repositoryが
提供する``grammar.js``から生成された``parser.c``をC compilerでcompileします。``parser.c``は
AdocWeave Language ServerのRust parserではなく、Zedのsyntax highlighting用grammarです。

基本的な構文色付けはTree-sitter queryが担当します。段落、見出し等のinline内容はinline grammarへ、source block本文は
指定された言語のgrammarへinjectionします。リンク、参照、anchor等の解析上の意味を補足するSemantic TokensはLSPが担当し、
基本色付けの成立条件にはしません。

== 通常のZedプロファイルへの導入

隔離しない場合も、Language Serverをbuildして``PATH``を設定した同じshellからZedを起動し、
``editors/zed``をdev extensionとして選びます。Zed公式文書によるuser dataの既定位置は次です。

[cols="1,3",options="header"]
|===
|OS |user data directory

|Linux
|`$XDG_DATA_HOME/zed`。未設定時は通常``~/.local/share/zed``

|macOS
|`~/Library/Application Support/Zed`

|Windows
|`%LOCALAPPDATA%\Zed`
|===

通常profileではextension関連状態もこのuser data配下に置かれます。一方、選択した
``editors/zed``は開発sourceのままであり、``adocweave-lsp``はリポジトリの``target/debug``にあります。
したがって、リポジトリを移動した場合や別shellからZedを再起動した場合は再導入または``PATH``の
再設定が必要になります。

== アウトライン設定

Zedの``settings.json``へ次を追加すると、Tree-sitter由来ではなくAdocWeave Language Serverが返す
文書シンボルをOutlineで利用できます。

[source,json]
----
{
  "languages": {
    "AsciiDoc": {
      "document_symbols": "on"
    }
  }
}
----

既存の``languages``または``AsciiDoc``設定がある場合は、対応するobjectへ
``"document_symbols": "on"``だけを追加します。

== 動作確認

``fixtures/zed/manual.adoc``で次を確認します。

* 言語selectorが``AsciiDoc``になります。
* 見出し、属性、強調、link、xref、list marker、block delimiter、comment等がthemeに応じて区別されます。
* Project DiagnosticsへAdocWeaveの診断が表示され、編集後に更新されます。
* Outlineへ文書タイトルと入れ子の見出しが表示されます。
* 見出しmarker後の空白診断で、Linuxでは``Ctrl+.``または
  ``editor: toggle code actions``から修正を適用できます。
* ``editor: format``を明示的に実行すると整形され、再実行しても変更が生じません。
* 見出しへhoverするとlevel、生成IDおよび対象部分が表示されます。
* ``[source, ru]``の``ru``直後で``Ctrl+Space``を実行すると``rust``が候補に出ます。
* ``[,rust]``のlisting blockは``[source,rust]``と同じ言語注入を受けます。``source-language``による既定言語は
  tree-sitter queryだけでは文書属性を解決できないため、Zed上では明示指定したblockを確認対象とします。
* 明示anchorとxrefでDefinitionおよびFind All Referencesが動作します。
* xref targetはLinux／Windowsでは``Ctrl+クリック``、macOSでは``Cmd+クリック``で開けます。通常クリックは
  Document Linkを開く操作ではありません。

基本色付けをLSPから分離して確認する場合は、Zedの``settings.json``へ一時的に次を設定します。

[source,json]
----
{
  "languages": {
    "AsciiDoc": {
      "semantic_tokens": "off"
    }
  }
}
----

この状態でも基本色付けが残ることを確認します。続いて``"semantic_tokens": "combined"``へ変更し、LSP起動後に
リンク、参照、anchor、literalおよびformulaの意味的補足を重ねても、見出し等が不自然に上書きされないことを確認します。
light／darkの標準themeを一つずつ使いますが、特定のRGB値ではなく構文同士を判別できることを確認対象とします。

太字または斜体が通常本文と視覚的に同じ場合は、コマンドパレットから
``dev: open highlights tree view``を開き、対象範囲に``emphasis.strong``または``emphasis``が付いているか確認します。
captureがあればqueryは成立しており、具体的な色、weight、italic faceはthemeとeditor fontの表示能力に依存します。
captureがなければinline grammarへのinjectionまたはhighlight queryの問題として扱います。

保存時の行末空白削除はZed自身の設定でも発生するため、それだけをFormat Document成功の根拠に
しません。コマンドパレットから``editor: format``を明示的に実行します。

== 問題の切り分け

``zed: open log``でZed logを開きます。foreground起動時は同じ内容の一部をterminalでも確認できます。

`failed to install the wasm32-wasip2 target`::
Zedが使用するRustが``rustup``管理か確認し、同じtoolchainへ``rustup target add wasm32-wasip2``を実行します。

``grammars/asciidoc/src/parser.c``がない::
grammar repositoryの取得結果または``extension.toml``のrepository、commit、pathが不整合です。
AdocWeaveのRust parserをCへ変換する必要はありません。取得cacheを消して再導入する前に、Zed logに表示された
grammar checkoutが固定commitと一致することを確認します。

``adocweave-lsp``の取得または起動に失敗する::
local buildを使う場合は``command -v adocweave-lsp``と``$PWD/target/debug/adocweave-lsp --version``を、Zedを起動する
shellで確認します。managed binaryを使う場合はZed logにあるinstallation statusを確認し、versionと同じGitHub Releaseに
manifestと対象platformのLSP assetがあることを確認します。

AsciiDocとして認識されるが色付けされない::
dev extensionを再導入して、Zed logに``asciidoc``と``asciidoc_inline``のgrammar build失敗がないことを確認します。
``cargo make check-zed``は固定grammarとqueryのnode／capture仕様を、``cargo make test-zed-release-package``はqueryのarchive同梱を検査します。
Semantic Tokensを``off``にしても色付けされない場合はLSPではなくgrammarまたはquery側の問題です。

``wasi-sdk-temp``内のsymlinkまたはinotify watch errorが出る::
``--user-data-dir``が開いているworkspaceの内側にないか確認します。WASI SDK取得の完了後にgrammarと拡張がcompileされていれば、
一時展開をworktree監視が観測しただけです。次回は上記のように``/tmp``へ隔離profileを作ります。SDK取得またはcompile自体が
失敗している場合だけbuilder障害として扱います。

== 検証後の削除

隔離手順を使った場合はZedを終了してから、表示して控えた``$ZED_DEV_DATA``だけを削除すれば、今回作成したZedの
設定、DB、拡張およびcacheをまとめて除去できます。Language Serverのbuild成果物は通常のCargo
``target``に残るため、他の開発成果物と同じ扱いにします。Zedが拡張source directoryへ生成する
``extension.wasm``とgrammar build directoryもリポジトリの無視対象であり、不要なら同時に削除できます。

[source,console]
----
printf '%s\n' "$ZED_DEV_DATA"
test -n "$ZED_DEV_DATA"
rm -rf -- "$ZED_DEV_DATA"
rm -rf editors/zed/extension.wasm editors/zed/grammars
----

通常profileへ導入した場合はExtension GalleryからAdocWeave dev extensionを削除します。Zed全体の
user data directoryを削除すると他の拡張、設定、DBおよびlogも失われるため、清掃目的でdirectory
全体を削除してはいけません。
